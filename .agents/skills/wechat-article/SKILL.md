# WeChat Article Harness

Use the project CLI as the only production control plane. It owns runs, Agent threads, artifacts, rendering, QA, upload, and WeChat draft side effects.

For workflow or tooling fixes, separate product verification from article delivery. Run local tests, real rendering and mocked publishing/handoff boundaries by default. A request to fix the workflow does not require generating, recreating or updating a real article draft. If the user excludes draft generation, do not run live draft operations or keep asking for draft authorization; complete the workflow-only acceptance instead.

- Run from `/Users/miller/Projects/wechat-agent`. For a topic, run `pnpm --dir scripts/wechat wechat-agent topic "<topic>" --vault /absolute/vault --audience "..." --angle "..."`.
- For an existing Markdown draft, run `pnpm --dir scripts/wechat wechat-agent improve <article.md> --vault /absolute/vault --goal "..." --cover <image>`.
- Use `status`, `resume`, `preview`, and `report` to inspect an existing run. Do not edit `.runtime/runs` manually.
- For custom body illustrations, use `revise <run-id> --scope content --patch <json> --assets <json>`. The asset map is `{"chart.svg":"/absolute/project/.runtime/editorial-inputs/chart.svg"}`; reference `../assets/chart.svg` in the patched Markdown beside the relevant explanation. Use distinct safe filenames and self-contained SVGs or raster images inside the project. The CLI copies and fingerprints every referenced image, reruns rendering and QA, then uploads and verifies them all. Do not force a generic diagram at the end; automated visual generation only supports explicitly referenced sequential diagrams.
- All rendered articles begin with one plain-language paragraph that introduces the project and naturally leads into the topic. Never label it “项目引子” or “项目因子”, and never use a field list, table of contents, duplicate title card or English kicker. Chapter one starts with the necessary project background. Use `revise <run-id> --scope layout --remove-title-card` to migrate an existing draft without changing its body, cover, diagrams or other template text.
- New articles review the outline before drafting, then use independent structure and style editors. They edit only the current article; the factual baseline is evidence, not a competing working copy. Use `--style neutral|conversational|khazix` for an explicit voice, and only claim it after independent style QA passes.
- Existing articles use `revise <run-id> --scope references|image|layout|content|style`. Every revision keeps global deterministic checks and locked scope validation. Pure references or fixed template-row removal use deterministic acceptance; an opening-only content patch whose later body, headings, images and cover are unchanged uses first-screen QA; other revisions use full visual QA. Never expand a small fix into a full rewrite or add a task-specific production wrapper.
- Commands: `--scope references` numbers source names and keeps full visible URLs; `--scope image --font-scale 0.75` changes only SVG text; `--scope layout --image-width 50` changes display width; `--scope content --patch /absolute/patch.json` applies unique before/after replacements; `--scope style --style khazix --goal "..."` rewrites the current article. Versions are immutable; `--version N` starts a revision from a saved version. `retry` reruns a known blocked stage, not a sent publication request.
- `--local-only` explicitly permits local review without remote access and permanently forbids draft mutation for that run and its descendants. If the target draft disappeared, do not silently recreate it; report the failed readback and request the user's decision.
- Read [editorial rules](references/editorial-rules.md) for writing or revising. Read [publishing rules](references/publishing-rules.md) before a draft action. Read [conflict resolution](references/conflict-resolution.md) whenever the run pauses on facts.
- After finishing an article or revision, automatically open that article's latest verified draft page in the current task's Codex right-side browser panel, not an external browser; do not wait for another request to open it. Use `open_in_codex` with `placement: "right"` and a browser target. Follow the draft handoff rules below and in the publishing rules.

The original Vault Markdown is never modified. `export <run-id> --output <vault-path>` is the only route that writes the final work copy back into the Vault.

After verified sync, use the CLI `handoff` result for the exact `open_in_codex` arguments. Reuse the saved `tabId` only within the same task and target draft. Otherwise use permitted in-app tab inventory to find this task's previous verified draft URL and pass that observed id with the latest URL; never select an unrelated tab by title. Persist the actual tool result via `handoff <run-id> --status queued|opened --tab-id <observed-id>`. Queued stays queued until visible confirmation. Do not close unrelated tabs or repeatedly create previews. If inventory is unavailable or blocked, report it and do not bypass the browser restriction.

Visual QA requires a vision-capable model. One QA call returns both the verdict and first-screen evidence; it must read the opening project keyword or block rather than using OCR workarounds. Full QA receives the first screen, overlapping segments and the cover; an opening-only revision receives only the first screen and cover; deterministic revisions do not call a model. Agent timeouts are 90s for scoped QA, 240s for full QA and 600s for other roles. `status` exposes the current run operation, and a second mutation of the same run is rejected until the first finishes. After a remote draft write, recovery uses a readback-only `verify-draft` path instead of writing again.

When the user explicitly says “创建草稿” or “更新草稿”, call `approve-draft <run-id>` or `update-draft <run-id> --media-id <media-id>` directly. The CLI persists the approved action and exact target; never ask the user to copy a token. Never invoke a mass-send or publication action; this harness has no such command. Return only a real draft URL when available; otherwise return the actual `media_id` and say the URL is unavailable.

For the automatic draft handoff, use a fresh successful readback of the target article. The real preview URL may be in `publish/readback.json` at `response.news_item[0].url` even when the run reports `pending_editor_url`; match the article and `media_id` before opening. Call `open_in_codex` with `placement: "right"` and `target: { type: "browser", url: verifiedDraftUrl }` in the current task. Opening an external browser or merely returning a link does not fulfill this preference. Do not open an obsolete draft as though it contains local-only changes. If no current draft URL exists or opening is blocked, state the limitation without inventing a URL or bypassing browser restrictions. This default opening preference does not authorize mass-send or publication.
